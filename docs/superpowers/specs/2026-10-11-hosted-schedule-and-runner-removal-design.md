# FreePli 일정 취소와 GitHub 단독 실행 설계

- 작성일: 2026-10-11
- 상태: 설계 초안 — 구현 전 검토 필요
- 대상: FreePli Studio 일정 관리 및 제작 실행 경로
- 범위: 일정 취소·목록 정리, GitHub-hosted 실행으로 전환, PC 실행기 제거
- 제외: 음악·영상 생성 엔진 재작성, 기존 산출물 재렌더링, 업로드 정책 변경

## 문제와 목표

현재 일정의 원본, 제작 요청 상태, PC 실행기 상태가 한 화면에서 이어지지 않는다. PC 실행기나 로컬 상태가 없으면 예정 작업이 진행되지 않을 수 있고, 목록에서 항목을 지워도 다른 상태 스냅샷이 이를 다시 표시할 위험이 있다.

목표는 다음과 같다.

1. 웹앱에서 일정을 취소하고 활성 일정 목록에서 제거할 수 있다.
2. 아직 외부 작업에 제출되지 않은 제작도 함께 취소할 수 있다.
3. 제출·실행되었거나 게시된 작업은 일정 제거만으로 중단하거나 삭제하지 않는다.
4. 승인된 일정은 기존 제작 엔진을 재사용해 GitHub-hosted Actions에서 실행한다.
5. 전환이 검증되기 전까지 PC 실행기와 기존 일정을 보존한다. 검증 완료 후에만 PC 실행기를 등록 해제하고 제거한다.
6. 음악 생성, 완곡 영상·숏폼 제작 및 YouTube 업로드 로직은 변경하지 않는다.

## 확인된 현황과 확인이 필요한 부분

- 로컬 Studio 코드에서는 일정 저장과 제작 실행 상태가 서로 다른 경로로 나타났고, 로컬 PC 커넥터는 로컬 일정/프로젝트 상태를 대시보드 스냅샷으로 게시하는 구조였다.
- 모바일 실행기 저장소에는 GitHub-hosted `cloud-advance.yml`이 `ubuntu-latest`에서 주기적으로 실행되고 수동 제어 workflow도 있다. 현재 hosted workflow가 일정 목록을 직접 읽어 실행하는지는 확인되지 않았다. 구현 때 기존 엔진과 상태 기록을 추적해 연결해야 한다.
- Studio 배포 저장소의 현재 기본 브랜치에는 정적 사이트 파일과 자산이 보인다. 실제 편집 원본 및 배포 입력 경로가 이 저장소와 일치하는지 먼저 확인해야 한다.
- 로컬에 5곡 일정 파일이 있으나, 이는 현재 서버 측 일정의 권위 있는 목록으로 간주하지 않는다. 각 항목을 요청 ID, Kaggle 작업, Drive 산출물, YouTube 게시 ID와 대조하기 전에는 취소·이전·삭제하지 않는다.
- 따라서 현재 일정이 모두 미실행 상태라고 가정하거나 일괄 취소하지 않는다. 먼저 정확한 원본·요청·외부 ID를 교차 확인한다.

## 사용자가 승인한 취소 규칙

일정의 “삭제”는 활성 일정 목록에서 숨기고 취소 이력을 남기는 동작이다. 저장된 제작 요청, 게시 이력, 산출물 자체를 지우는 뜻이 아니다.

- Kaggle 제출·실행 전에 있고, Drive 산출물 및 외부 게시 ID가 없는 요청만 `cancelled` 처리하고 일정 활성 목록에서 제거한다.
- 취소 직전에도 상태와 외부 ID를 다시 조회한다. 상태가 바뀌었거나 확인할 수 없으면 취소하지 않고 목록과 이력을 보존해 사용자에게 확인 필요 상태를 표시한다.
- Kaggle 제출이 시작됐거나 커널/배치가 존재하거나, Drive 산출물·YouTube 게시 ID가 있으면 일정 제거만으로 작업을 중단하거나 결과를 삭제하지 않는다. 일정 취소를 거부하고 현재 상태와 이유를 보여준다.
- 이미 게시된 항목은 일정만 제거할 수 없다. 별도 플랫폼 삭제 기능은 이번 범위에 없다.
- 중복 클릭과 동시 실행에는 조건부 상태 갱신(CAS)과 멱등 키를 사용한다. 충돌 시 최신 상태를 다시 읽으며, 취소/실행 요청을 맹목적으로 재전송하지 않는다.
- 취소된 항목은 감사 가능한 tombstone으로 보존하고 다시 활성화할 때 원래 ID를 재사용하지 않는다.

## 목표 흐름

1. 사용자가 웹앱에서 일정과 제작 내용을 확인한다.
2. 저장만 한 일정은 `scheduled` 상태이며 제작을 시작하지 않는다.
3. 사용자가 해당 일정의 제작 시작을 명시적으로 승인한다. 승인에는 콘텐츠 ID, 목표 공개 시각, 대상 형식, 기존 산출물 재사용 정책이 묶인다.
4. GitHub 상태 저장소에 승인 기록과 고유 요청 ID를 조건부로 기록한다.
5. GitHub-hosted Actions가 정기 실행 시각을 확인하고, due 승인 일정만 같은 요청 ID로 기존 `cloud-advance` 엔진에 전달한다.
6. 엔진은 기존 Kaggle 제출·생성, Drive 보관, YouTube 예약 업로드, 후처리 흐름을 계속 사용한다. 기존 결과물 또는 전달 ID가 있으면 새 렌더·업로드를 만들지 않고 동일 작업을 재개하거나 이미 완료로 판정한다.
7. 웹앱은 GitHub 상태와 Actions 실행 기록을 읽어 진행 상태를 표시한다. PC 실행기 실행 여부는 일정 저장·진행·완료의 조건이 되지 않는다.
8. 늦게 실행되어 목표 예약 시각을 지킬 수 없거나 상태가 불명확하면 즉시 공개하지 않는다. 해당 요청을 안전하게 멈추고 사용자 조치 필요 상태로 보고한다.

## 상태와 식별자

일정과 제작 요청의 상태를 분리한다.

- 일정: `scheduled`, `approved`, `cancelled`, `completed`, `needs_attention`
- 제작 요청/플랫폼 전달 상태는 현재 스키마를 우선 재사용한다. 이 설계에서 새 상태 체계를 병렬로 만들지 않는다.
- 일정 ID는 영구 고유값이며 제작 요청 ID는 결정론적으로 일정 ID에서 생성한다. 외부 제출 전에 GitHub 상태에 고정하고 이후 재시도에서도 같은 값을 사용한다.
- 기록에는 콘텐츠 ID, 생성원 일정 ID, 승인 시각, 목표 공개 시각과 시간대, Actions run ID, Kaggle 식별 정보, Drive 산출물 참조, 플랫폼 게시 ID/URL, 마지막 전이 시각을 둔다.
- 비밀값, OAuth 토큰, 업로드 세션 URI는 상태 JSON이나 UI에 넣지 않는다.

실제 필드명과 기록 위치는 현행 스키마·API를 조사한 뒤 기존 형식에 맞춘다. 새 데이터베이스나 워크플로 프레임워크는 도입하지 않는다.

## 일정 제거 화면

- 활성 일정 목록에 취소 버튼을 제공한다.
- 클릭 후 서버의 최신 상태를 확인하고, 외부 제출 전임이 검증된 경우에만 취소한다.
- 성공하면 목록에서 숨기되 상세 이력/감사 기록은 보존한다.
- 진행 중·외부 ID 존재·상태 불명확일 때는 제거 대신 상태와 이유를 표시한다. 일정 삭제가 제작 중단을 의미한다고 오해하게 만들지 않는다.
- 일괄 취소는 이번 범위에서 지원하지 않는다.
- 예전 로컬 스냅샷이 취소 항목을 다시 활성화하지 못하도록 GitHub 상태의 취소 이력을 우선하고 로컬 스냅샷은 일정 원본으로 사용하지 않는다.

## GitHub-hosted 전환과 PC 실행기 제거

- GitHub-hosted `ubuntu-latest`만 실행 위치로 허용한다. `self-hosted`, PC 예약 작업, PC 실행기 온라인 상태를 요구하는 경로를 새 실행 흐름에서 금지한다.
- 기존 hosted workflow와 기존 제작 엔진을 연결하고, 별도의 엔진/스케줄러를 만들지 않는다.
- 스케줄 탐색 및 시작은 기존 `cloud-advance` 주기를 재사용한다. 한 번의 주기 지연은 가능하며, 실제 주기·최대 대기 시간은 구현 후 workflow에서 확인해 UI에 사실대로 표시한다.
- GitHub Actions concurrency 또는 상태 잠금으로 같은 일정을 두 실행기가 동시에 처리하지 못하게 한다.
- 인증과 비밀은 현재 GitHub Secrets/기존 인증 경로를 재사용하며 로그에 원문을 출력하지 않는다.
- 삭제 순서: hosted dry-run 및 상태 전이 테스트 → 미게시 테스트 요청의 hosted 검증 → 예약/Drive/YouTube 경로 확인 → PC 실행기 제거 확인 → 마지막으로 등록 해제·서비스 중지·설치 제거.
- 이전 중에는 PC 실행기 설치와 설정을 보존한다. hosted 경로가 실제로 검증되지 않았거나 미해결 요청이 있으면 PC 실행기를 제거하지 않는다.
- 제거 대상은 FreePli 전용 runner 등록·서비스·실행 파일·전용 자격 파일로 한정한다. 공용 GitHub CLI, 사용자가 별도로 쓰는 자격증명, 결과물과 상태 이력은 지우지 않는다. 제거할 구체 경로와 GitHub runner ID는 구현 전에 확인한다.

## 이전 및 안전한 컷오버

1. 실제 Studio 소스 저장소와 Pages 배포 경로를 식별한다.
2. 현재 서버 일정, 로컬 일정, cloud requests, Actions run, Kaggle 작업/커널, Drive 산출물, YouTube 게시 ID를 일정별로 대조한다.
3. 각 항목을 미실행/진행 중/완료/불명확으로 분류한다. 불명확한 항목은 이동·취소하지 않는다.
4. 승인 전 일정은 자동 제작으로 보내지 않는다. 명시적으로 승인된 일정만 hosted scanner가 읽는다.
5. 새 상태 저장 경로를 배포하기 전에 dry-run에서 due 선택, 멱등 키, 취소/충돌 동작을 검증한다.
6. 기존 일정을 이전할 때는 원래 ID·게시 시각·상태를 보존하고, 같은 일정의 중복 request 생성을 금지한다.
7. 일부 일정만 먼저 검증하고, 기존 PC runner를 둔 채 hosted 경로를 시험한다.
8. hosted end-to-end 동작과 외부 부작용 중복 방지를 검증한 뒤 PC runner를 제거한다.
9. 실제 예약 콘텐츠를 즉시 공개하거나 이 설계 검증용으로 새 콘텐츠를 생성하지 않는다.

## 오류 처리

- 네트워크/일시 오류: 기존 엔진의 제한적 재시도 정책을 그대로 사용한다.
- 인증 오류, 정책 제한, 공개 시각을 놓칠 위험, 외부 ID 불일치: 자동 재시도·새 제출을 하지 않고 `needs_attention`으로 기록한다.
- GitHub API 409/422 또는 조건부 갱신 충돌: 현행 상태를 다시 fetch하고 같은 ID/기존 외부 ID를 확인한 뒤, 상태가 안전할 때만 재개한다. 요청 내용을 덮어쓰거나 중복 제출하지 않는다.
- Actions 실행 실패: run ID와 정제된 오류 요약을 저장한다. 원시 로그, 토큰, 세션 URI는 UI와 상태 파일에 노출하지 않는다.
- Kaggle GPU 잔여량이 부족하거나 확인할 수 없으면 새 작업을 제출하지 않고 보고한다.
- 일정 공개 시각에 대한 허용 지연이나 missed-deadline 자동 보정 정책은 이 설계에서 임의로 정하지 않는다. 늦은 작업은 즉시 공개하지 않고 사용자 확인을 요구한다.

## 검증과 완료 기준

- 취소는 외부 제출이 확실히 없을 때에만 성공한다.
- Kaggle 제출 ID, Drive 산출물 또는 게시 ID가 하나라도 존재하면 일정 삭제가 거부되고 이력이 보존된다.
- 상태 불명확, 동시 취소/실행, API 충돌은 실패 폐쇄하며 중복 request나 외부 부작용이 없다.
- 취소 tombstone은 로컬 스냅샷 동기화 후에도 일정 목록에 되살아나지 않는다.
- 승인되지 않은 일정은 스케줄러가 시작하지 않는다.
- 동일 일정의 중복 dispatch와 반복 workflow 실행은 기존 요청 ID로 한 번만 외부 작업을 시작한다.
- workflow job의 runner가 GitHub-hosted임을 검증하며 `self-hosted` runner 없이 dry-run/상태 검증이 통과한다.
- 기존 생산 엔진 회귀 테스트를 수행하고 실제 외부 게시를 수반하지 않는 검증과 실제 운영 검증을 분리해 보고한다.
- 검증 전에 runner를 제거하지 않는다. runner 제거 후 PC 실행기 없이 상태 조회와 승인된 일정 처리가 가능한지 확인한다.
- 제작·Drive 업로드·YouTube 업로드의 운영 성공은 실제 실행 증거가 있을 때만 완료로 보고한다.

## 위험과 대응

- 일정 저장소가 둘 이상이면 오래된 스냅샷이 항목을 되살릴 수 있다. GitHub 상태를 유일한 권위 경로로 만들고 로컬 데이터는 이전 완료 후 읽기 전용/제거한다.
- GitHub-hosted 실행 간격에 따라 늦을 수 있다. 지연 경고를 표시하고 공개 시각을 넘긴 작업은 자동 즉시 공개하지 않는다.
- Kaggle·Google Drive·YouTube 인증과 할당량은 별도 서비스에 의존한다. 인증/할당량 확인을 제출 전 게이트로 둔다.
- hosted 경로와 기존 PC runner가 동시에 실행되면 중복 제작이 가능하다. 공통 잠금·멱등 요청 ID와 보수적 컷오버를 적용한다.
- 일정 삭제를 결과물 삭제로 오해할 수 있다. 화면에서 두 작업을 명확히 구분한다.

## 단계 밖 항목

- 음악·영상 생성 모델 또는 템플릿 변경
- 새 음악 생성, 재렌더링, 실제 YouTube 공개/즉시 공개
- 이미 제출된 Kaggle 작업이나 게시된 영상의 강제 중단/삭제
- 다른 플랫폼 업로드 구현
- PC 외 자격증명이나 공용 GitHub 도구 제거
- 생산 엔진/워크플로 프레임워크 교체
